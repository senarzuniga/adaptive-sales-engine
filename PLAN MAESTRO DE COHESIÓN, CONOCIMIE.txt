2.1. Sistemas coexistentes

A. React/Vite

- Dispone de aproximadamente 25 rutas.
- Contiene UI, reglas comerciales, mapeadores, normalizadores y fallbacks.
- Usa Supabase y localStorage.
- Implementa el flujo documental más conectado.

B. Streamlit/Python

- Contiene autenticación, navegación, páginas y agentes.
- Usa session_state y acceso opcional a Supabase.
- Mezcla páginas reales, páginas duplicadas y contenido demo.
- Debe convertirse en la única aplicación.

C. Supabase Edge Functions

- Contienen análisis, prompts, validación e ingestión valiosos.
- Parte de la lógica de negocio reside aquí, separada de Python.
- Varias funciones usan service role sin autorización suficiente.

D. Agentes Python

- Algunos realizan análisis reales.
- Otros son heurísticos, incompatibles o stubs.
- El orquestador ejecuta agentes por descubrimiento dinámico, sin contrato
  uniforme ni selección basada en capacidades.

E. ai-factory-v2

- Contiene scraping, extracción, normalización e inteligencia.
- Funciona como librería/prototipo.
- No está conectado al ciclo principal ni dispone de persistencia real por
  defecto.

F. Launchers, scripts y aplicaciones auxiliares

- Existen varias entradas Streamlit, monitores y launchers.
- Hay rutas obsoletas y nombres incorrectos.
- El worker de ofertas no se ejecuta de forma permanente.

2.2. Duplicaciones principales

- Dos aplicaciones de usuario completas.
- Tres mecanismos de ingestión.
- Dos o más modelos de Action y Offer.
- Varias formas de representar customer/contact/company.
- Estado repartido entre Supabase, localStorage y session_state.
- Páginas Streamlit importadas y posteriormente redefinidas.
- Múltiples manifiestos de dependencias.
- Varios launchers para procesos que no forman un ecosistema coherente.

2.3. Contratos incompatibles

Ejemplo Action:

- Python: name, goal, department, status="open".
- Supabase: title, company_id, priority, status="todo".
- React: estructura y estados propios.

Ejemplo Offer:

- Python: serial_number, total_amount, status.
- Supabase/React: offer_number, total_value, company_id.
- Existe además compatibilidad especulativa con status_v2.

Estas incompatibilidades obligan a usar fallbacks que ocultan errores de
esquema.

2.4. Flujos parcialmente conectados

- Documentos React -> Edge Function -> Supabase: conectado, con
  inconsistencias de mapeo.
- Oferta -> pipeline_jobs: crea trabajo, pero el worker es manual.
- ai-factory-v2: pipeline útil, no llamado desde la aplicación principal.
- trigger-ingestion: invocado desde React, pero la función no existe.

2.5. Conclusión de cohesión

El repositorio tiene muchas capacidades, pero no forma todavía un sistema.
La prioridad debe ser reducir ambigüedad antes de aumentar funcionalidad.

3. PRINCIPIOS NO NEGOCIABLES
======================================================================

1. Streamlit será la única aplicación de usuario.
2. Supabase/Postgres será la única fuente de verdad.
3. session_state será sólo estado de interfaz.
4. localStorage dejará de ser persistencia comercial.
5. Toda entidad pertenecerá a una organización.
6. Toda recomendación deberá indicar evidencia, confianza y versión.
7. Ninguna inferencia de IA sobrescribirá hechos sin revisión o regla
   explícita.
8. Los documentos y datos originales serán inmutables.
9. No se realizarán fusiones destructivas.
10. Todos los agentes usarán contratos tipados.
11. Los agentes no escribirán directamente en la UI.
12. Las acciones externas requerirán autorización humana.
13. Cada trabajo será idempotente, observable y reintentable.
14. No se eliminará código antiguo hasta demostrar paridad.
15. La madurez se medirá con evidencia de CI y uso, no con declaraciones.

El programa se divide en once fases. Cada fase dispone de un gate. Si el
gate no se cumple, no se avanza.

----------------------------------------------------------------------

Objetivo:

Detener riesgos inmediatos y congelar una referencia medible del sistema.

Trabajo:

1. Revocar las credenciales expuestas en el TXT.

3. Desactivar Quick Access por defecto.

5. Inventariar entornos, proyectos Supabase, buckets y secretos.
6. Generar un backup lógico y físico antes de migrar.
7. Capturar datasets de referencia anonimizados.
8. Registrar las rutas, funciones, tablas, agentes y scripts actuales.
9. Identificar propietarios funcionales por dominio.
10. Congelar nuevas funcionalidades hasta aprobar el modelo canónico.

Entregables:

- registro de activos;
- registro de secretos;
- baseline de esquema;
- catálogo de datasets;
- mapa de dependencias;
- suite inicial de fixtures;
- registro de riesgos;
- copia restaurable.

Gate 0:

- cero secretos versionados;
- Quick Access desactivado en producción;
- backup restaurado con éxito en un entorno aislado;
- inventario firmado por responsables;

- schema_version;
- created_at y updated_at UTC;

2.3. Reglas de modelado

- No Dict[str, Any] en contratos críticos.
- No DataFrame entre procesos.
- DataFrame sólo dentro de parsers o análisis.
- No nombres como claves naturales.
- Identificadores externos se guardan por sistema fuente.
- Estados son enums versionados.
- Moneda y unidad son explícitas.
- Fechas diferencian evento, validez y registro.

  -> leased
  -> running
  -> succeeded
  -> retryable_failed
  -> terminal_failed
  -> cancelled
  -> dead_letter

Conocimiento:

raw
  -> validated
  -> proposed
  -> approved
  -> rejected
  -> superseded
  -> retracted

Oferta:

draft
  -> under_review
  -> approved
  -> sent
  -> accepted / rejected / expired

FASE 4. INGESTIÓN, CALIDAD Y ESTRUCTURACIÓN DE CONOCIMIENTO

Objetivo:

Crear un pipeline único para datos estructurados, documentos y fuentes
externas.

4.1. Pipeline único

Fuente
  -> registro
  -> cuarentena
  -> hash/dedupe
  -> parseo
  -> normalización
  -> extracción
  -> validación
  -> reconciliación
  -> revisión humana
  -> publicación
  -> generación de conocimiento
  -> reanálisis comercial.

4.2. Formatos

- CSV;
- XLSX;
- JSON;
- PDF;
- DOCX;
- imágenes/OCR;
- email;
- URL;
- datos CRM/ERP futuros;
- fuentes de mercado.

4.3. Calidad

Dimensiones:

- completitud;
- validez;
- consistencia;
- unicidad;
- actualidad;
- trazabilidad;
- exactitud;
- coherencia referencial.

Cada lote tendrá:

- filas recibidas;
- aceptadas;
- rechazadas;
- duplicadas;
- pendientes;
- score de calidad;
- errores por campo;
- responsable de revisión.

- ID externo;
- NIF/VAT;

- similitud de nombre;
- dirección;
- teléfono;

Una coincidencia probabilística crea un match_candidate. No elimina filas.

Tablas:

- merge_decision;
- conflict_case;
- resolution_decision.

- identidad de cliente;
- estado de oferta;
- cambio de precio;

Gate 4:

13. RIESGOS Y MITIGACIONES
======================================================================

Riesgo: borrar React antes de migrar reglas.

Riesgo: migrar datos inconsistentes.
Mitigación: staging, candidatos, reconciliación, revisión.

Riesgo: intentar construir todos los módulos a la vez.
Mitigación: oleadas y gates.

Riesgo: IA sin evidencia.
Mitigación: assertion/evidence obligatoria.

Riesgo: fuga entre tenants.
Mitigación: RLS, tests, storage privado.

Riesgo: costes LLM.
Mitigación: presupuesto, caché, reglas deterministas y supervisor.

Riesgo: Streamlit lento.
Mitigación: queries paginadas, caché, jobs asíncronos, materialized views.

Riesgo: modelos y estados vuelven a divergir.
Mitigación: contratos versionados generados desde una fuente canónica.

Riesgo: documentación no refleja realidad.
Mitigación: documentación generada desde esquema, contratos y CI.

Riesgo: módulo "completo" sin adopción.
Mitigación: acceptance tests y piloto por rol.

16. CONCLUSIÓN
======================================================================

La visión descrita en el informe original es alcanzable, pero no mediante
la acumulación de más pantallas, agentes o tablas sobre el repositorio
actual.

Primero debe construirse una semántica única y una base verificable. La
calidad del futuro motor comercial dependerá más de:

- procedencia;
- validación;
- consistencia;
- seguridad;
- contratos;
- trazabilidad;
- operación;

que del número de agentes o módulos.

Una vez fijada esa base, Streamlit puede convertirse en la aplicación
completa y única. React y las Edge Functions actuales deben tratarse como
fuentes de reglas, contratos y comportamiento a migrar, no como residuos
que puedan borrarse inmediatamente.

El resultado final deberá cerrar este circuito:

FUENTE
  -> DATO INMUTABLE
  -> VALIDACIÓN
  -> HECHO CANÓNICO
  -> CONOCIMIENTO CON EVIDENCIA
  -> INSIGHT
  -> RECOMENDACIÓN
  -> APROBACIÓN
  -> ACCIÓN
  -> RESULTADO
  -> APRENDIZAJE MEDIDO

Cuando este circuito sea seguro, observable y reproducible, Adaptive Sales
Engine será realmente un motor comercial adaptativo y no una colección de
aplicaciones y prototipos independientes.
